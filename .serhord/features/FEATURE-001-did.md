# FEATURE-001 · DID-акаунти та авторизація

**Статус:** 📦 ready · **Модуль:** `src/did.ts` · **Клас:** `DidAccount`

## Проблема

Зараз користувач — «Guest»: без ідентичності, без можливості підписувати дії,
без переносного акаунта. Для меш-мережі (FEATURE-002) і AI2AI (FEATURE-004)
потрібен криптографічний ідентифікатор, який:

- не потребує сервера реєстрації;
- дозволяє перевіряти «це справді ця нода» (підписи);
- переноситься між пристроями (бекп ключа).

## Рішення

**W3C DID у методі `did:key`** на базі ECDSA P-256 (WebCrypto — нуль залежностей):

1. Генерація пари ключів у браузері, приватний ключ — `extractable` лише для
   збереження в IndexedDB (далі — експорт у зашифрованому вигляді, див. ризики).
2. Публічний ключ → стиснута форма (33 байти) → multicodec `0x1200` →
   multibase base58btc → `did:key:z6Mk…` (реалізовано власноруч, без бібліотек).
3. DID-документ за специфікацією W3C (`verificationMethod`, `authentication`).
4. **Авторизація = володіння ключем:** challenge–response (`challenge()` →
   `signChallenge()` → `verifyChallenge()`, nonce + 5-хвилинне вікно).
   Жодних паролів, жодних серверів.

## API поверхня

| Метод | Що робить |
|---|---|
| `load()` | відновлює акаунт з IndexedDB |
| `create(alias)` | генерує пару, зберігає, повертає профіль |
| `updateProfile(patch)` | аліас/колір/біо |
| `document()` | W3C DID-документ |
| `sign(data)` / `verify(did, pubJwk, data, sig)` | підпис/перевірка |
| `challenge()` / `signChallenge()` / `verifyChallenge()` | безпарольний вхід |
| `short()` | `did:key:z6Mk…f3Xq` для UI |

## Інтеграція (план, фаза 1)

- Налаштування → вкладка **«Identity»**: створення/імпорт, аліас, резервна копія.
- Сайдбар: чип Guest → аліас + `short()`; тултіп з повним DID.
- Меш: кожне повідомлення підписується цим ключем (вже так у FEATURE-002).
- Перший запуск: модалка «Створити ідентичність / Пізніше».
